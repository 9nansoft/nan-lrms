# แผนแก้ไข: ประเด็นจากรีวิว Agent + Assessment Sync 3 ตาราง

## Context

รีวิวพบว่า agent (`agent/`) ทำงานได้จริงและ sync assessment 3 ฟอร์ม (`asm_first_pregnant_pt_nan` / `asm_lr_record_birth_period_nan` / `asm_lr_record_after_birth_nan`) ถูกต้องตามดีไซน์ — แต่มี bug จริง 1 ตัว (clear-cache ไม่ลบ cursors), พฤติกรรม agent ผิด intended 2 จุด (ไม่เคารพ permanentBlock, `localGateway` ไม่มีผลกับการ probe) และความเสี่ยง hardening อีกหลายจุด ผู้ใช้เลือก **"แก้ครบทุกอย่าง"**

## A. Bug หลัก

### A1. clear-cache ลบ cursors ด้วย
`src/app/api/admin/clear-cache/route.ts:28-31` — เพิ่ม `DELETE FROM cached_maternity_assessment_cursors` ถัดจากบรรทัดลบ metadata (cursors ไม่มี FK กับแถว จึงลบลำดับไหนก็ได้ในกลุ่มนี้) พร้อมอัปเดต comment ให้เหตุผลชัด ("cursor ที่รอดทำให้แถวใต้ cursor ไม่ถูกดึงกลับหลัง clear")
- Test: ต่อ `tests/unit/api/assessment-cache-wipe.test.ts` — seed cursor row + assert 0 rows หลังเรียก clear-cache route (ใช้ pattern เดิมของไฟล์)

### A2. Agent เคารพ permanentBlock + backoff เมื่อ push ตาย
`agent/src/index.ts` — ให้ `cycle()` คืนสถานะ `{ blocked: boolean }` โดย blocked = `result.permanentBlock` หรือ error ตรง `/browser-push HTTP 401|403/` (key ถูก revoke) แล้ว main loop (บรรทัด 139-144) ใช้ exponential backoff: เริ่ม 30 นาที ×2 ขึ้นไป ห้ามเกิน 6 ชม. (cap 360 นาที), reset เป็น interval ปกติเมื่อ cycle สำเร็จ — ไม่ spam 403 ทุก 5 นาที แต่ก็กลับมาเองได้เมื่อ admin re-onboard/reactivate
- แยก logic การคำนวณ wait เป็น pure function `nextWaitMs(intervalMinutes, backoffMinutes, blocked)` ในไฟล์ใหม่ `agent/src/backoff.ts` เพื่อ unit test ได้
- แก้ cosmetic ที่พบพร้อมกัน: heartbeat ใน catch-path รายงาน `mode: 'unknown'` แทนค่า default `'local'` เมื่อยังไม่รู้ mode จริง
- Test: ใหม่ `tests/unit/agent/backoff.test.ts` (pattern ตาม `tests/unit/agent/gateway-session.test.ts`)

### A3. `localGateway` config มีผลจริงกับการ probe
- `src/lib/bms-browser-client.ts:803-851` — `probeLocalApi(config, marketplaceToken, localApiUrl: string = LOCAL_API_URL)` แล้วใช้ `${localApiUrl}/api/sql` / log / apiUrl swap ตาม param (browser เรียกแบบเดิม → ไม่เปลี่ยนพฤติกรรม)
- `agent/src/session.ts:124` — `acquireSession` ส่ง `localGateway` เข้า `probeLocalApi` เป็นตัว probe
- `agent/src/config.ts:113` — strip trailing `/` ของ localGateway เหมือน serverUrl
- Test: เพิ่มเคส "probe ใช้ URL ที่ส่งเข้ามา" ใน test suite ของ bms-browser-client (หาไฟล์เดิมใน `tests/unit/` ตอน implement)

## C. Hardening ฝั่ง sync

### C1. Lock กัน pull ชนกันข้าม path
ปัญหา: `inFlightHospitals` ใน `src/services/sync/assessment-schedule.ts:41` กันได้แค่ scheduler-vs-scheduler — push path (`push-handler.ts:691`) และ backstop (`polling.ts:1302`) วิ่งซ้อนกับ reconcile ได้ → prune อาจลบแถวใหม่ชั่วคราว
- สร้าง `runAssessmentPullExclusively<T>(hospitalId, fn): Promise<T | null>` (คืน null เมื่อมี pull ของโรงพยาบาลนั้นกำลังรัน) ใน `src/services/sync/maternity-assessment.ts` เก็บ Set บน `globalThis.__assessmentPullLocks` (pattern เดียวกับ `_global.__assessmentSyncSchedule` — กันปัญหา module instance แยกกันใน Next.js)
- 3 callers: `assessment-schedule.ts` pullHospital (แทน Set เดิม), `push-handler.ts:691` (lock ไม่ว่าง → `appendSyncStep` status success/skipped ข้อความ "another assessment pull is in flight — skipped, scheduler catches up within 5 min"), `polling.ts:1302` (skip + log)
- Test: ใน `tests/unit/services/sync-maternity-assessment.test.ts` — concurrent call ครั้งที่สองได้ null; และเคส push ตอน lock ไม่ว่าง ใน `tests/unit/api/agent-push.test.ts`

### C2. Pin timezone convention ของ window ให้ explicit
ปัจจุบันความสอดคล้องของ `recorded_at >= '<date>'` (cache) vs `assessment_head_datetime >= '<date>'` (HOSxP) พึ่งพา Node tz == PG session tz โดยปริยาย (ดู comment `maternity-assessment.ts:766-777`)
- **ตรวจก่อนเริ่ม**: ยืนยัน type คอลัมน์ `recorded_at` (TIMESTAMPTZ ตาม `src/db/schema-sync.ts:19`) และรูปแบบ string ที่ `usableTimestamp` คืน (`src/services/maternity-assessment-fields.ts`) — ถ้าพบว่าคอลัมน์เป็น naive timestamp อยู่แล้ว ให้ทำเฉพาะข้อ parse-pinning
- Parse pinning: HOSxP datetime ที่ไม่มี zone ให้ parse เป็น UTC ให้รู้เรื่อง ("นาฬิกา naive ของ HOSxP ติดป้าย UTC") ใน `maternity-assessment-fields.ts` — ค่าที่เก็บไม่ขยับใน deployment ที่รัน UTC (ซึ่งเป็น prod Docker)
- Prune pinning: `pruneDeletedAssessments` (`maternity-assessment.ts:819-844`) เปลี่ยน `recorded_at >= ?` เป็น `(recorded_at AT TIME ZONE 'UTC') >= ?` — เทียบ naive clock กับ literal เดียวกับที่ HOSxP เทียบ ไม่ขึ้นกับ session tz
- อัปเดต doc comment ของ `reconcileWindowStart` ให้บอก convention ที่ pin ไว้
- Test: normalize เก็บค่า zone-less แบบกำหนดได้; prune เทียบ naive (แถวที่ HOSxP ลบใน window ถูกลบ, นอก window อยู่รอด)

### C3. Reconcile window แบ่งหน้า (แก้ "ฟอร์มยุ่ง >500 แถว prune ไม่ได้")
- `src/config/hosxp-queries.ts` — `buildAssessmentReconcileSqlFor(table, pk, since, afterPk?)` เพิ่ม `AND t.<pk> > {{AFTER_PK}}` (substitution guard `^\d{1,18}$` เหมือน {{SINCE}} เดิม)
- `pullMaternityAssessmentsFromHosxp` (`maternity-assessment.ts:1040-1067`) — loop keyset pagination: ดึงหน้าละ `ASSESSMENT_ROW_LIMIT` เรียงตาม pk จนหน้าสั้นกว่า limit → `windowComplete = true`; ครบ cap 20 หน้า (10,000 แถว) โดยยังไม่จบ → `windowComplete = false` (ปลอดภัยไว้ก่อน เหมือนเดิม)
- Test: `tests/unit/config/hosxp-queries-assessments.test.ts` (guard afterPk) + `sync-maternity-assessment.test.ts` (fake client คืน 2 หน้า → windowComplete=true, และเคส cap)

### C4. Backfill `patient_id`
`syncMaternityAssessments` (`maternity-assessment.ts:378`) — หลัง upsert รัน 1 statement:
```sql
UPDATE cached_maternity_assessments a
   SET patient_id = (SELECT p.id FROM cached_patients p
                      WHERE p.hospital_id = a.hospital_id AND p.an = a.an
                      ORDER BY p.created_at LIMIT 1),
       updated_at = ?
 WHERE a.hospital_id = ? AND a.patient_id IS NULL AND a.an IS NOT NULL
```
(subquery + ORDER BY กันกรณี AN ซ้ำ; ปกติ update 0 แถว ไม่แพง) นับจำนวน backfill ใส่ log
- Test: sync แถวที่เคยเก็บตอน patient ยังไม่มี → รอบถัดมา patient_id ถูกเติม

### C5. Purge guard ครอบ cursor + metadata write
- `advanceAssessmentCursors` (`maternity-assessment.ts:732-764`) — INSERT/UPDATE เพิ่ม `WHERE NOT EXISTS (SELECT 1 FROM hospital_bms_config WHERE hospital_id = ? AND data_purged_at IS NOT NULL)` เหมือน row-INSERT (บรรทัด 447-449)
- `src/services/assessment-metadata-cache.ts` (write 124-200) — เพิ่ม purge guard ใน upsert ใน transaction เดียวกัน
- Test: purge ระหว่าง pull → cursor/metadata ไม่ถูกเขียน

### C6. เทียบ hint แบบ BigInt
`src/lib/browser-poll.ts:1174-1177` — `Number(maxPk) > Number(cursor)` เพราะ PK ยาวได้ถึง 18 หลัก เกิน 2^53: เทียบด้วย `BigInt` เมื่อค่าทั้งคู่ตรง `/^\d+$/` fallback เป็น Number เดิม (กระทบแค่ trigger — server เป็นคนดึงจริง ความเสียหายต่ำแต่แก้ถูกจุด)

## นอกขอบเขตรอบนี้ (แจ้งไว้ชัด)
- **`updated_at` bump ทุก reconcile**: การทำ DO UPDATE แบบมีเงื่อนไขจะทำให้ `RETURNING` คืนชุดว่างเมื่อแถวไม่เปลี่ยน ซึ่งโค้ดปัจจุบันตีความว่า "purged ระหว่างเขียน" แล้วหยุด batch (`maternity-assessment.ts:485-492`) — ต้องออกแบบ sentinel ใหม่ แยกเรื่อง
- **Token-once เมื่อ token เก่า/ถูก rotate**: ต้องมี admin endpoint ล้าง token บังคับ — ต้องการ product decision
- **Delete ที่เกิดหลัง 7 วัน**: documented limitation ของ design (window 7 วัน) — ไม่ใช่ bug
