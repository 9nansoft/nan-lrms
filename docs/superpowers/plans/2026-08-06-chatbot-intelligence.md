Source: 12-agent extraction workflow (2026-08-06). Three adversarial critics converged on
the build order below. The feasibility critic VERIFIED LIVE against

## Rank 1 — Unblock tool calling: tool-aware LLM client surface + bounded agent loop [critical/M]

**Fixes:** "HN 530012 ตอนนี้เป็นยังไง", "ใครเสี่ยงสูงบ้างตอนนี้", "รพ.ชุมแพมีคนรอคลอดกี่คน" — the model can only see the 10 newest cached_patients rows in one static block and cannot look anything up. Worse: if tools were sent today, the first tool-calling response (content: null) hits `throw new Error('LLM returned empty content')` at llm-client.ts:166, the route catches at route.ts:56 and the nurse gets 502 'ผู้ช่วยแชทไม่พร้อมใช้งาน'.

**Design:** A) src/lib/llm-client.ts — widen the transport WITHOUT changing existing dev-simulation behaviour: add `role: 'tool'`, `tool_call_id?`, `tool_calls?` to LlmChatMessage; add `tools?: ChatCompletionTool[]` and `toolChoice?: 'auto'|'none'|'required'` to LlmChatOptions; extend ChatCompletionResponse to model `message.tool_calls`; export a NEW `llmChatRaw(opts): Promise<{content: string|null; toolCalls: LlmToolCall[]; finishReason?: string; usage?: {...}}>` that never throws on null content, and keep `llmChat()` as a thin wrapper over it that preserves the existing empty-content throw so llmJson/dev-simulation callers are byte-identical. Add `sanitizeToolCalls(raw)` — drop any call whose `arguments` string fails JSON.parse and coerce '' to '{}' (a truncated arg echoed back into the next request 400s the whole conversation). B) NEW src/services/chat/agent-loop.ts exporting `runChatTurn(messages: LlmChatMessage[], ctx: ChatToolContext, opts: {tools; maxRounds; sampling}): Promise<{answer: string; trace: ToolTraceEntry[]}>` — round 0..N-1 `tool_choice:'auto'`; on the LAST round send NO tools + `tool_choice:'none'` plus a Thai finish nudge ('สรุปคำตอบจากผลที่ได้มาแล้ว ห้ามเรียกเครื่องมือเพิ่ม') because tool_choice:'none' alone invites next-step narration; if the loop exits with tool results but no text, run one unconditional synthesis-only pass. Dedupe on `name::JSON.stringify(args, sortedKeys)` — a repeat becomes a synthetic tool message ('เรียกเครื่องมือนี้ด้วยพารามิเตอร์เดิมไปแล้ว ให้ใช้ผลเดิมและสรุปเป็นข้อความ') rather than a re-execution. C) src/config/clinical-chat-config.ts — add `maxToolRounds` (default 4) and per-tool budget caps to ClinicalChatLimits; fix `numEnv` so it accepts 0 (currently `raw > 0` silently forces CLINICAL_CHAT_TEMPERATURE=0 back to 1.0, making deterministic statistics answers unconfigurable). D) chat-service.ts calls runChatTurn instead of llmChat.

## Rank 2 — Real tool registry over existing dashboard services, behind one scope/PDPA-enforcing chokepoint [critical/M]

**Fixes:** Every question that needs a lookup or an aggregate the static block doesn't carry: "ใครเสี่ยงสูงบ้าง" (getHighRiskPatients exists, unreachable), "7 วันที่ผ่านมาแนวโน้มเป็นยังไง" (getTrends exists, unreachable — completely unanswerable today), "มีอะไรต้องรีบจัดการบ้าง" (getDashboardAlerts), "รพ.10670 มีคนรอคลอดกี่คน", "คำนวณ CPD ให้หน่อย" (calculateCpdScore is pure and free). tools.ts + tool-router.ts have ZERO non-test importers — 80 lines of test-green, production-dead code.

**Design:** A) NEW src/config/clinical-chat-tools.ts — config-driven, no hardcoded conditionals in the loop: `CHAT_TOOL_SURFACE: Record<ClinicalChatMode, readonly string[]>` so statistics mode sees aggregate-only tools and clinical mode sees patient-scoped ones, plus `TOOL_BUDGET: Record<string, number>` (default 3) so a small model cannot loop the same query 12×. B) NEW src/services/chat/tool-registry.ts — `interface ChatToolSpec { tool: ChatCompletionTool; scope: 'hospital' | 'province'; execute(ctx: ChatToolContext, args: Record<string,unknown>): Promise<unknown> }` and `const CHAT_TOOL_REGISTRY: Record<string, ChatToolSpec>`. Entries thinly wrap EXISTING services (constitution: reuse, no new SQL): `search_patients` → getHospitalPatientList(db, ctx.hospitalCode, {status, riskLevel, page, perPage}) then re-mask — dashboard.ts:606 DECRYPTS `name`, so the wrapper MUST run maskName() and drop cid before returning, and must project to an allow-list (hn, an, maskedName, age, gaWeeks, riskLevel, laborStatus, cpdScore, partographSeverity); `list_high_risk` → getHighRiskPatients (same re-mask, decrypts at :382); `get_trends` → getTrends; `get_alerts` → getDashboardAlerts; `get_stage_kpis` → getStageKPIs; `get_province_dashboard` → getProvinceDashboard; `get_maternal_screen_summaries` → listMaternalScreenSummariesForHospital (already PHI-free); `score_cpd` → calculateCpdScore (pure, zero DB); existing `get_patient_context`. Descriptions are written as mini-policies in Thai: **ใช้เมื่อ** / **อย่าใช้เมื่อ — ใช้ <tool อื่น> แทน**, so the model resolves tool choice at prompt-read time. C) REWRITE src/services/chat/tool-router.ts as `runChatTool(call: LlmToolCall, ctx: ChatToolContext): Promise<{ toolMessage: LlmChatMessage; ok: boolean }>` — the single door, mirroring runTool's ordering: unknown-name gate → mode-surface gate → per-tool budget charge → hospital-scope gate (`scope==='hospital' && !ctx.hospitalCode` → refusal naming the province tool to use instead) → execute → `recordToolOutcome(ctx.ledger, ...)`. EVERY bail path returns the SAME shape as success: `{role:'tool', tool_call_id, content: JSON.stringify({error, reason, action})}` — never a throw, so a refusal is in-band training signal the model self-corrects from on the next round. D) `ChatToolContext = { db; hospitalCode?: string; mode: ClinicalChatMode; ledger: DataQueryLedger; budget: Map<string, number>; now: Date }` — the per-turn state bus (mutable ledger by reference) that makes rank 3 and 4 possible at all.

## Rank 3 — Per-turn data ledger + zero-data claim guard (never ship an invented count) [critical/M]

**Fixes:** The mirror image of the P0 that is being fixed now. Once tools are live, the dangerous failure flips from "ไม่มีข้อมูล" to a fluent fabrication: a query fails or gets scope-refused, and the model still answers "ขณะนี้มีผู้ป่วยรอคลอด 12 ราย ANC 45 ราย" because it knows the SHAPE of the answer. A nurse acting on an invented labor-ward census is a clinical-safety incident, and the current statistics system prompt ('ห้ามเดาตัวเลขเอง') is a prompt plea the model can ignore.

**Design:** NEW src/services/chat/grounding.ts. (a) `export interface DataQueryLedger { succeeded: number; failed: number }` and `createDataLedger()`; `recordToolOutcome(ledger, toolName, resultJson)` counts ONLY data tools (a closed `NUMERIC_GROUNDING_TOOLS` set from src/config/clinical-chat-tools.ts — search_patients, list_high_risk, get_trends, get_alerts, get_stage_kpis, get_province_dashboard, get_patient_context, score_cpd) and classifies a payload carrying an `error` key as failed. Deliberately EXCLUDE get_current_datetime — a clock read is well-formed JSON and must never count as 'we measured something'. It is called from runChatTool AFTER execute, so a scope/budget/unknown refusal records nothing. (b) `enforceDataClaimGrounding(answer, {ledger, toolResults, priorTranscript, threshold})`: fail-open ladder — no ledger → return identity; `ledger.succeeded > 0` → identity (rank 4 owns that turn); zero successes AND `measurementDigits(answer).length >= threshold` (default 2, from config) → one temp-0 regen, ACCEPTED ONLY if the regen actually dropped below threshold, else the deterministic Thai fallback 'ตอนนี้ยังดึงข้อมูลจากฐานข้อมูลไม่สำเร็จ จึงยังไม่มีตัวเลขที่ยืนยันได้ค่ะ — กรุณาลองใหม่อีกครั้ง หรือแจ้งผู้ดูแลระบบ'. (c) `measurementDigits(text)` is the false-positive control and matters MORE here than in the reference because correct Thai zero-data replies offer candidate periods: strip ISO datetimes, d/m/y, clock times, and Thai-prose dates built from the same closed month table rank 6 introduces, THEN match /\d{2,}/, then drop both CE (19xx/20xx) and Buddhist-era (25xx) years. (d) Subtract figures already present anywhere in the prior transcript so 'สรุปเป็นตารางให้หน่อย' restating last turn's numbers is not refused. Wire it in chat-service.ts immediately after runChatTurn returns, before memory persistence.

## Rank 5 — Fix memory: scope by mode+hospital, persist the QUESTION not the context block, persist the CERTIFIED answer [high/S]

**Fixes:** Three live defects a nurse feels immediately. (1) chat-service.ts:92 persists `userTurn`, which contains the ENTIRE rendered statistics table — so up to 10 stale province snapshots are re-sent on every request, contradicting the fresh block ('ทำไมตัวเลขไม่ตรงกัน') and burning the token budget that ranks 1-2 now need for tool results. (2) memory-store.ts:20 keys on userId alone, so a user who moves from the province dashboard (statistics) to a hospital ward page (clinical) carries statistics tables into the clinical conversation and vice-versa. (3) Once ranks 3-4 land, the model would still REMEMBER its ungrounded draft — the number stripped from the screen gets restated with full confidence next turn.

**Design:** A) src/services/chat/memory-store.ts — `sessionKey(userId, mode, hospitalCode?)` → `kk-lrms:chat:mem:${mode}:${hospitalCode ?? 'province'}:${userId}`; change `getChatHistory`/`appendChatTurn` signatures to take a `ChatMemoryScope = {userId; mode; hospitalCode?}` object (TS strict makes every call site update mechanical). Move MAX_HISTORY_TURNS and SESSION_TTL_SECONDS into clinical-chat-config.ts (`chatMemoryLimits()`) so they are tunable per deploy, per constitution. B) src/services/chat/chat-service.ts — persist `{role:'user', content: question}` (the raw question ONLY; the freshly built context block is injected into THIS request's user turn but never stored) and `{role:'assistant', content: certifiedAnswer}` (the output of the rank 3+4 pipeline, not the loop's draft). Tool call/result rounds stay out of memory entirely — they are turn-scoped evidence, not conversation. C) Optional but cheap: also skip memory writes when the answer degraded to a fallback, so an infra blip does not poison the next three turns.

## Rank 8 — Request guardrails on /api/chat: rate limit, audit log, and free-text CID scrubbing [high/S]

**Fixes:** Three gaps that ranks 1-2 make materially worse. (1) No rate limit — src/lib/rate-limit.ts exists and is used by api/referrals/check but /api/chat never calls it, so one authenticated user (or a stuck retry loop in the panel) can burn unbounded GPU; with multi-round tool loops each request is now 2-5 LLM calls, not one. (2) Zero logAudit calls anywhere in src/services/chat or src/app/api/chat — clinical Q&A over patient data is completely unrecorded, and the audit trail is exactly what a PDPA review asks for. (3) The user's raw message is forwarded verbatim (chat-service.ts:66); a nurse typing a real patient name or a 13-digit CID sends unmasked PHI to the inference endpoint, defeating the careful masking in context-builder.

**Design:** A) src/config/clinical-chat-config.ts — `chatRateLimit(): {perWindow: number; windowSeconds: number}` (defaults 20 / 60). B) src/app/api/chat/route.ts (and the rank-7 stream route) — after auth, `await checkRateLimit(\`chat:${userId}\`, ...)`; on deny return 429 with an ACTIONABLE Thai message per constitution V ('ส่งคำถามถี่เกินไป กรุณารออีก N วินาที') and a Retry-After header, and NEVER reach fetch. C) NEW src/services/chat/input-guard.ts — `scrubUserMessage(text): {text: string; redactions: number}` reusing maskCid from src/lib/pii-mask.ts: replace any bare 13-digit run with its masked form before the message enters the prompt or memory. Deliberately narrow — do not attempt name detection (false positives would mangle real clinical questions); the CID is the one high-confidence, closed-shape identifier. D) chat-service.ts — call `tryLogAccess(db, {...})` once per turn with `action:'CHAT_QUERY'`, the hospitalCode, mode, the ORDERED tool names invoked, ledger {succeeded,failed}, whether the answer degraded, duration and token usage — and explicitly NOT the question text or the answer (logging free-text PHI would recreate the very leak (C) closes). Use tryLogAccess, not logAccess, so an audit write failure never fails the nurse's answer.
